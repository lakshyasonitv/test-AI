## 1. Exploration and discovery: crawling, button-driven SPAs, forms, state explosion, destructive actions, login

### Takeaway
Every vendor that explores autonomously (Octomind, QA Wolf Mapping Agent, Momentic, Autify Genesis, Rainforest) runs an LLM agent in a real browser that acts like a user, not a link crawler. The two non-crawling approaches learn flows from recorded real-user sessions instead: Meticulous records and replays them, and Checksum learns from them. Vendors are open about login handling: they detect the login wall, ask a human for credentials, and turn login into a reusable dependency test. None of the official sources found documents how they avoid destructive actions during exploration. The closest analogues are Meticulous's full network stubbing and Octomind's explicit teardown tests.

### Cited Findings

- At sign-up the agent takes a screenshot and suggests starter tests. It first checks for a cookie banner and a required login, because "their functionality is usually a prerequisites for all the other tests". If it finds a login, it asks for test credentials, generates and runs a login test, and "It will be added as dependency for other tests." **[OFFICIAL DOCS]** — [Octomind: Test recommendation at sign-up](https://octomind.dev/docs/build-tests/recommended-tests)
- Credentials work only for username/password logins, "not for social logins". The docs also say Octomind can handle 2FA and captcha in login flows. **[OFFICIAL DOCS]** — [Octomind: recommended tests](https://octomind.dev/docs/build-tests/recommended-tests); [Octomind: create first tests](https://octomind.dev/docs/get-started/create-first-tests)
- The agent "automatically generates up to 3 meaningful tests. If successful, it validates the tests and files them as 'active'." Once a project exists, "you can let the AI agent browse through your site to discover and generate more tests. Click on discover." **[OFFICIAL DOCS / VENDOR MKTG]** — [Octomind: Autogenerate tests](https://octomind.dev/docs/build-tests/autogenerate-tests); [Octomind: generate tests](https://octomind.dev/product/generate-tests)

**Academic background on button-driven (event-based) SPA crawling**
- Crawljax scans the DOM for "candidate elements that are capable of changing the state" and fires events on them. It "incrementally infers a state machine" of states and transitions, with clickables "which may change with every click". It backtracks to explore other paths and detects cycles. **[ACADEMIC]** — [Mesbah et al., ICSE 2009 (Crawljax)](https://people.ece.ubc.ca/amesbah/resources/papers/icse09.pdf); [Mesbah et al., TSE 2011](https://people.ece.ubc.ca/amesbah/resources/papers/tse11.pdf)
- The RIA crawling survey makes four points. Deciding whether a post-event DOM is a new state is "an important challenge". You must "choose an appropriate DOM equivalence relation", since text content is often irrelevant. The crawler "has to explore all the possible events from all the discovered states". "Loading a URL in the RIA leads to the initial state of that URL", and that is how a crawler resets. **[ACADEMIC]** — [Choudhary et al., "Crawling Rich Internet Applications: The state of the art" (2012)](https://www.site.uottawa.ca/~bochmann/Curriculum/Pub/2012%20-%20Crawling%20Rich%20Internet%20Applications%20-%20The%20state%20of%20the%20art.pdf)
- AutoE2E (ICSE 2025) explores breadth-first, "queuing and recursively crawling neighboring states", until no new states appear or a timeout is hit. It infers features from actions with an LLM, using probabilistic scoring by observed frequency. It reports 79% average feature coverage on E2EBench, "558%" above the best baseline. **[ACADEMIC]** — [Alian et al., arXiv 2408.01894](https://arxiv.org/abs/2408.01894v2)
- A third-party write-up of the AutoE2E repo says that for each queued state the tool builds an LLM context from "a screen capture of the State, the context of the previous State, and the HTML of the Action element", and "executes its non-critical actions". This suggests a critical/non-critical split to avoid state-changing actions during exploration, but it was not verified against the paper. **[THIRD-PARTY]** — [zenn.dev write-up of AutoE2E](https://zenn.dev/mima_ita/articles/ce1185307264a5?locale=en)
- VISCA (follow-up work) argues that AutoE2E's HTML-snippet feature inference lacks context. It adds multimodal UI-component abstraction and reports 92% feature coverage. **[ACADEMIC]** — [arXiv 2506.04161](https://arxiv.org/abs/2506.04161)

**Destructive-action guardrails (general agent-safety sources, not test-tool specific)**
- Recommended practices are tiered permissions (autonomous, needs approval, never), read-only or simulated environments, "mocking destructive endpoints (delete, send, pay)", and approval gates on state-changing actions. **[THIRD-PARTY]** — [Apidog: AI agent guardrails](https://apidog.com/blog/ai-agent-guardrails/)
- A research paper on testing LLM agents on the open internet uses a context-sensitive monitor that "enforces a stringent safety boundary to stop an unsafe test". **[ACADEMIC]** — [arXiv 2311.10538](https://arxiv.org/abs/2311.10538v1)

### Inferences
- In this market, "discovery" means an LLM agent in a live browser whose action space is every interactive element, not just `<a href>`. Button-driven SPA navigation is covered because the agent clicks whatever it sees. The academic precedent for doing this deterministically is Crawljax-style event-based crawling with a DOM-state equivalence function.
- Octomind's retreat from free auto-generation to human-chosen recommendations is a signal. Unsupervised exploration produced too much noise to file automatically, so the market settled on agents that propose and humans that pick.
- No vendor document found says how agents avoid "Delete account" or "Place order" while exploring. The safest documented patterns are Meticulous (stub every request, so exploration has no backend side effects) and Octomind (explicit teardown tests restore state). AutoE2E's apparent "non-critical actions only" rule is a third option, unverified.
- Login is handled the same way everywhere: detect it, ask a human for credentials, then make login a dependency or seed that later tests reuse.

### Gaps
- No primary source describes **how** Octomind's, QA Wolf's or Momentic's explorers bound state explosion (depth or breadth limits, state equivalence), or whether they skip destructive controls.
- AutoE2E's critical/non-critical action split could not be verified because the search budget was exhausted.
- Checksum's official docs on session-based flow detection were not surfaced. All Checksum flow-learning claims are third-party.
- Virtuoso's and Functionize's autonomous exploration: no documentation of an exploration or crawl mode was found. Virtuoso's StepIQ is described only as "analyzes the UI and proposes steps" ([Virtuoso: QA practitioner](https://www.virtuosoqa.com/solutions/qa-practitioner), **[VENDOR MKTG]**).

## 2. Turning natural language into tests: live per-step execution vs generate-then-validate, avoiding hallucinated elements and steps, DOM/a11y vs vision, human review

### Takeaway
The dominant pattern is **interleaved act-observe-write**. The agent performs each step in a live browser, observes the resulting state, and only then commits the step and its locator. This holds for the Playwright Generator, QA Wolf, Reflect's agent, Rainforest, Virtuoso Live Authoring and Autify Genesis. A separate **verify-by-running** pass then follows (QA Wolf Verifier, Octomind "validates… files as active"). Hallucination is controlled by making the model choose from elements that exist on the current page (accessibility snapshot refs), not by asking it to describe them. Every vendor puts a human approval step before tests or fixes become active.

### Cited Findings
**Playwright Test Agents and Playwright MCP (the most transparent reference design)**
- The three agents form a pipeline. "Planner explores the app and produces a Markdown test plan", the "Generator transforms the Markdown plan into Playwright Test files", and the "Healer executes the test suite and automatically repairs failing tests". Each agent is "a collection of instructions and MCP tool definitions", run by a coding assistant (VS Code Copilot, Claude Code). Definitions "should be regenerated whenever Playwright is updated". **[OFFICIAL DOCS]** — [playwright.dev: Test agents](https://playwright.dev/docs/test-agents)
- The Generator "performs the scenarios live, verifies selectors and assertions, uses generation hints, and has a catalog of assertions for structural and behavioral validation". Generated tests "can still contain initial errors that Healer may address". This is official-doc wording relayed by third-party guides, not read directly. **[THIRD-PARTY quoting OFFICIAL]** — [Medium: Complete guide to Playwright agents](https://medium.com/@ismailsobhy/ai-powered-test-automation-part-4-complete-guide-to-playwright-agents-planner-generator-healer-d418166afe34); [TestMu: Playwright agents](https://www.testmuai.com/blog/playwright-agents/)
- The agents were introduced in Playwright v1.56 and run with `npx playwright init-agents --loop=vscode|claude`. **[THIRD-PARTY]** — [TestDino: Playwright test agents](https://testdino.com/blog/playwright-test-agents/); [Currents: State of Playwright AI ecosystem 2026](https://currents.dev/posts/state-of-playwright-ai-ecosystem-in-2026)
- Playwright MCP "uses accessibility snapshots instead of screenshots", described as "structured representations of web page content based on the browser's accessibility tree". Each interactive element gets a ref such as `ref=e5`, which `browser_click` and `browser_type` use to target it. Refs "are valid until the page changes, after which a fresh snapshot returns new refs". **[OFFICIAL DOCS]** — [Playwright MCP: snapshots](https://playwright.dev/mcp/snapshots); [Playwright MCP: introduction](https://playwright.dev/mcp/introduction); [Mintlify mirror: accessibility snapshots](https://www.mintlify.com/microsoft/playwright-mcp/concepts/accessibility-snapshots)
- Vision is opt-in (`--vision`). It "works best with computer use models that are able to interact with elements using X Y coordinate space". For canvas-heavy pages the docs suggest taking a snapshot and a screenshot together. **[OFFICIAL DOCS]** — [Playwright MCP: snapshots](https://playwright.dev/mcp/snapshots)
- Known limits of accessibility-tree agents: "Canvas elements are opaque to it", and icon-only buttons without labels appear with no name. A hybrid of tree plus selective vision reportedly reached about 85% on WebGames versus about 50% for prior agents. **[THIRD-PARTY]** — [TinyFish: What browser agents see before they think](https://current.tinyfish.ai/issue/31/foundations/article/18062/what-browser-agents-see-before-they-think)

**QA Wolf (multi-agent, code output)**

The Code Writer "generates open-source Playwright code". The Verifier "runs the test code to make sure it works as intended". Inputs include "video, transcripts, DOM snapshots, and browser logs". ### Inferences
- Generate-then-validate in one shot, which is roughly what our pipeline does today for later screens, is not how any of these tools author tests. Every documented generator observes the screen a step will act on *before* writing that step. Validation-by-running is a second gate on top, not a replacement.
- Choosing by ref is the structural anti-hallucination mechanism. In Playwright MCP the model can only click `ref=eN` values from the current snapshot, and a new snapshot is mandatory after the page changes. An invented element therefore cannot be expressed.
- Decoupling "what to test" (Planner Markdown, QA Wolf AAA outline, testRigor case names) from "how to do it on this screen" (Generator, Code Writer) is common. The human review point sits on the plan or outline, which is cheap to review.
- Accessibility tree or DOM is the default modality. Vision is a fallback for canvas and unlabeled icons, or a secondary signal (Momentic, Rainforest).

### Gaps
- No source quantifies hallucination rates for any vendor's generator.
- testRigor docs do not say outright whether "generate an actual test" executes in a browser step by step. The per-step screenshots strongly imply it.
- Official text of the Playwright Generator's "assertion catalog" was not read directly (fetch blocked).

## 3. Representation: plain-English steps resolved by AI at runtime vs compiled code; trade-offs in determinism, cost and flakiness

### Takeaway
There are two camps. **Runtime-resolved natural language** (testRigor, Momentic, Reflect, Virtuoso hints, Rainforest) keeps the English step as the source of truth and resolves it against the live page each run, usually through a cache. **Compiled code** (QA Wolf, Octomind, Checksum, Autify Nexus export, Playwright agents) emits Playwright code once and runs it deterministically, adding AI only around failures. The runtime camp narrows its cost and determinism gap by caching resolved elements (Momentic claims more than 99% cache hits). The compiled camp narrows its brittleness gap with runtime wrappers and healers.

### Cited Findings
- **testRigor**: tests are English, "one step per line", parameters in quotes, and "each command used should look exactly like it's shown in the documentation", so the grammar is constrained, not free prose. Tests target "elements on the screen that are visible to an actual user", and "in most cases there's no need to identify element locators". **[VENDOR TRAINING]** — [testRigor: Basics](https://testrigor.com/certification/basics-of-testrigor/)
- testRigor "translates high-level instructions into a more specific set of steps". Its example expands "purchase a Kindle" into search, enter, and click "Kindle" then "Add to cart". **[VENDOR MKTG]** — [testRigor homepage](https://testrigor.com/)
- **Momentic**: it "starts from the step description rather than from a selector". A step is "cached with the element's position, appearance, text, and its accessibility and structural context". When those signals stop matching, "the locator agent resolves the description against the current DOM, the run continues, and the cache entry is updated", and the fix applies only to that run without editing the test file. **[VENDOR BLOG]** — [Momentic: Self-healing test automation guide](https://momentic.ai/blog/self-healing-test-automation-guide)
- Momentic step cache. Stored signals include "CSS selectors and HTML attributes, accessibility roles and metadata, screenshots and visual cues, and element location and dimensions". The runner replays "without invoking the LLM" on a match. Cache keys are "step's unique ID, IDs of any parent modules, the resolved element description, and dynamic template values". The cache is busted when "the target element changes significantly or if the templated description is different". Entries expire after 90 days inactive. Saving is limited to CI runs or non-protected branches. "AI check and AI extract are never cached." **[OFFICIAL DOCS]** — [Momentic: Step cache](https://momentic.ai/docs/reliability/step-cache)
- Momentic claims "over 99% of steps replay from that cache, 52ms slower than the equivalent Playwright call in our benchmark". **[VENDOR MKTG]** — [Momentic: Web app testing](https://momentic.ai/web-app-testing)
- **Virtuoso**: "When test steps are written in the natural English language, the page element automatically generates a Hint selector based on the text of the target element." **[THIRD-PARTY]** — [Perficient: Using Virtuoso commands](https://blogs.perficient.com/2023/03/28/using-virtuoso-commands). The first execution derives XPath or CSS identifiers that are used later. **[OFFICIAL KB]** — [Virtuoso KB: selector preference during authoring](https://knowledge.virtuoso.qa/hc/en-us/articles/19642758521373-Preference-in-choosing-the-selectors-during-element-identification-while-test-authoring)
- **Octomind**: test cases are YAML files in a `.octomind` directory in "dev mode", managed by CLI (`octomind pull` overwrites local files). **[OFFICIAL DOCS]** — [Octomind: dev mode commands](https://octomind.dev/docs/dev-mode/commands). Healing fixes are "written back to the test source as standard Playwright code". **[VENDOR MKTG]** — [Octomind: Playwright self-healing](https://octomind.dev/product/playwright-self-healing/). Octomind's runtime "wraps tests with smart waits, auto-retries, and trace recording", so flakiness is handled by the wrapper, not by an LLM at run time. **[VENDOR MKTG]** — [Octomind vs coding agents](https://octomind.dev/product/octomind-vs-coding-agents/)
- **Checksum**: "Since every test is standard Playwright code, you retain full ownership and can run the suite with or without Checksum." The runtime package adds the AI layers. **[PARTNER]** — [The CTO Club: Checksum in CI/CD](https://thectoclub.com/partner-spotlight/checksum/how-to-use-checksum-for-continuous-e2e-testing-in-ci-cd/); **[OFFICIAL package page]** — [npm @checksum-ai/runtime](https://npmjs.com/package/@checksum-ai/runtime)
- **Rainforest** concedes in its own comparison post that no AI-based QA tool is fully deterministic. **[VENDOR BLOG]** — [Rainforest vs QA.tech](https://www.rainforestqa.com/blog/rainforest-vs-qatech)
- **Meticulous** has no authored representation at all. The test is a recorded session (events plus network pairs) and the oracle is a screenshot diff. **[OFFICIAL DOCS]** — [Meticulous: Architecture overview](https://app.meticulous.ai/docs/concepts/architecture-overview)

### Inferences
- Momentic's cached step is close to what our IR is: a semantic description plus deterministic grounding fields (css, role, bbox), with the semantic part kept so the grounding can be re-derived. Its cache-key composition (step ID, parent module, resolved description, template values) mirrors this repo's "cache keys must include every real input dimension" rule.
- Compiled-code tools get determinism and portability (runnable without the vendor) and confine AI to authoring and healing. That is the same trade-off this project already made (`DECISIONS.md` D-06).
- The runtime-AI camp pays LLM cost only on cache misses and on AI assertions. AI assertions are the one place that stays non-deterministic in every run.

### Gaps
- No independent benchmark compares flakiness or cost between the two camps. The 52 ms and 99% figures are Momentic's own.

## 4. Element identification: testRigor "as a user sees it", Momentic AI locators, Reflect, Virtuoso hints and self-healing, Functionize ML

### Takeaway
All of these tools identify an element by **user-visible semantics** (visible text, label, role, relative position) and keep a **multi-signal fingerprint** (several selectors, attributes, role, bounding box, screenshot) as a cache or fallback. When duplicates exist, they disambiguate with relative position words, not by asking the model for a CSS path.

### Cited Findings
- **testRigor relative locations**: the element you want is the "target" and the reference element is the "anchor". Multiple relative locations are allowed in one command. When a second is added, the first one softens from "directly" to "roughly", and the keyword "completely" keeps it strict. A search summary also reports about 25 supported UI positions, which was not seen verbatim. **[VENDOR BLOG]** — [testRigor: Reference elements by UI position](https://testrigor.com/blog/how-to-reference-elements-by-ui-position-using-testrigor)
- testRigor Vision AI uses "computer vision algorithms to recognize and interact with UI components based on their visual appearance" instead of depending solely on code locators. **[VENDOR BLOG]** — [testRigor: Vision AI](https://testrigor.com/blog/vision-ai-and-how-testrigor-uses-it/)
- **Momentic** caches a multi-signal fingerprint and re-resolves from the description on mismatch. See section 3 for both sources. **[OFFICIAL DOCS / VENDOR BLOG]** — [Momentic: Step cache](https://momentic.ai/docs/reliability/step-cache); [Momentic blog](https://momentic.ai/blog/self-healing-test-automation-guide)
- **Virtuoso**: tests target elements with plain-English hints, and Virtuoso "applies heuristics to pick the most likely match". **[OFFICIAL DOCS]** — [Virtuoso: Elements and self-healing](https://docs.virtuoso.qa/guide/making-the-most-of-virtuoso/elements/). Steps can hold several selector types, and "the first one that returns a valid element is used". Duplicate hints are disambiguated with position words, for example "Click on top 'Login'". **[OFFICIAL KB]** — [Virtuoso KB: unexpected element type with same hints](https://knowledge.virtuoso.qa/hc/en-us/articles/19510251689501-Virtuoso-is-targeting-unexpected-element-type-that-has-the-same-hints). Virtuoso collects several IDs per element (XPath, XPath ID, CSS) as fallbacks. **[VENDOR BLOG]** — [Virtuoso: complex element selection in Salesforce](https://virtuosoqa.com/post/complex-element-selection-in-salesforce). Its best-practice page recommends hints over XPath, since over-reliance on XPath produces flaky tests. **[OFFICIAL DOCS]** — [Virtuoso: Best practice hints](https://docs.virtuoso.qa/guide/getting-started/best-practice-hints.html). A "Lock explicit selectors" toggle turns self-healing off for a step, per a search summary of Virtuoso docs/KB. The exact page was not pinned.
- **Reflect** "adapts to shifts in your app automatically" instead of depending on fragile selectors. **[VENDOR MKTG]** — [SmartBear Reflect](https://smartbear.com/product/reflect/)
- **Rainforest** uses "several different methods to reliably identify elements, including screenshots, DOM selectors, and AI-generated descriptions". **[VENDOR MKTG]** — [Rainforest platform](https://rainforestqa.com/our-platform). Sacra frames it as visual-first ("validates what users see"). **[THIRD-PARTY]** — [Sacra: Rainforest](https://sacra.com/c/rainforest)
- **Functionize** claims "99.95% accuracy in ML element tracking". Its FAQ says "deep learning ML models learn how your UI works", lists K-means, EM, RNN and CNN, and says that "every time a test is run, our Machine Learning Engine learns your site's DOM even better". **[VENDOR MKTG / OFFICIAL FAQ]** — [Functionize ML engine](https://www.functionize.com/ml-engine); [Functionize FAQ](https://support.functionize.com/hc/en-us/articles/33002707491607-Frequently-Asked-Questions)
- **Playwright MCP verification and locator tools** (`--caps=testing`): `browser_verify_element_visible` takes an ARIA **role and accessible name** taken from the snapshot. The group also includes `browser_verify_text_visible`, `browser_verify_list_visible`, `browser_verify_value` and **`browser_generate_locator`**, which generates a locator from an actual element. **[OFFICIAL DOCS (mirror)]** — [Playwright MCP: test assertions (Mintlify mirror)](https://www.mintlify.com/microsoft/playwright-mcp/tools/test-assertions); [Playwright MCP introduction](https://playwright.dev/mcp/introduction)
- **Octomind** healing "finds the intended element using context, accessible roles, and text labels" rather than the old selector. **[VENDOR MKTG]** — [Octomind: Playwright self-healing](https://octomind.dev/product/playwright-self-healing/)
- **Checksum runtime**: when a selector fails, stored element metadata is used to find the element. If that fails, a custom model regenerates the failed section. **[OFFICIAL package page]** — [npm @checksum-ai/runtime](https://npmjs.com/package/@checksum-ai/runtime)

### Inferences
- No tool asks the LLM to name a control's type in free text and then trusts that word. Identity comes from what is on the page (role and accessible name from the a11y tree, visible text, position relative to an anchor). Our weak point (4), where the LLM says "combobox" or "select" and that does not match the real control, is exactly the free-text type naming the market avoids.
- "Generate the locator from the chosen element" (Playwright MCP `browser_generate_locator`, Virtuoso deriving XPath/CSS on first run) is the shared pattern. The model never authors the selector.

### Gaps
- No public detail on how Momentic or Functionize weigh their signals, or what thresholds they use.

## 5. Assertions: AI-checked, visual, and how tools avoid vacuous or wrong assertions

### Takeaway
Tools offer three kinds of assertion: deterministic (text visible, element visible by role and name, value), visual-diff, and natural-language AI checks. The vendors themselves steer users toward deterministic checks where possible, warn that AI validations can hallucinate, and never cache AI checks. The strongest documented safeguard against wrong assertions is **verifying each assertion live at authoring time** (Playwright Generator) plus a **closed catalog** of assertion types.

### Cited Findings
- **Momentic AI check**: conditions are plain English, from narrow visual details to broad statements. The AI can read the full page HTML, but for visual information it only sees the visible area in a screenshot, so a scroll step may be needed first. **[OFFICIAL DOCS / SUPPORT]** — [Momentic: steps](https://momentic.ai/docs/core-concepts/steps); [Momentic support: How do I use AI check?](https://support.momentic.ai/articles/6419062127-how-do-i-use-ai-check)
- Momentic's mobile docs recommend `checkScreenContains` for exact-text checks "because it is deterministic and cheaper" than the natural-language `assert`. **[OFFICIAL DOCS]** — [Momentic mobile: assert](https://momentic.ai/docs/reference/mobile-commands/assert.md)
- Momentic never caches AI check or AI extract, so they hit the model every run. **[OFFICIAL DOCS]** — [Momentic: Step cache](https://momentic.ai/docs/reliability/step-cache)
- **testRigor**: `check that page "contains a positive message in the chat response" using ai` analyzes the page's UI and source. The docs warn that "AI models can occasionally produce incorrect results (hallucinations)". Deterministic forms are `check that page contains "..."` and `check that page doesn't contain`. **[VENDOR TRAINING]** — [testRigor: Validations](https://testrigor.com/certification/validations/); [testRigor: How to perform assertions](https://testrigor.com/blog/how-to-perform-assertions-using-testrigor)
- **Playwright Generator** "verifies selectors and assertions" live and "has a catalog of assertions for structural and behavioral validation". **[THIRD-PARTY quoting OFFICIAL]** — [Medium guide](https://medium.com/@ismailsobhy/ai-powered-test-automation-part-4-complete-guide-to-playwright-agents-planner-generator-healer-d418166afe34). The MCP verify tools return "Done" on success and an error on failure. One guide recommends that an agent not report completion until the expected state is confirmed, and cautions that these "are focused helpers, not an exhaustive assertion library". **[THIRD-PARTY]** — [qaskills: Playwright MCP testing capability](https://qaskills.sh/blog/playwright-mcp-testing-capability-guide-2026)
- **Meticulous**: there are no authored assertions. It "captures a visual snapshot after dispatching each event, and compares these snapshots to those generated for the base commit". The company says this also catches "broken buttons or bugs in business logic". **[OFFICIAL DOCS / VENDOR MKTG]** — [Meticulous: Architecture overview](https://app.meticulous.ai/docs/concepts/architecture-overview); [Meticulous: how it works](https://meticulous.ai/how-it-works)
- **Checksum**: when its model regenerates a failed section, it "may add, remove, or change actions but is meant to keep the assertions unchanged". **[OFFICIAL package page]** — [npm @checksum-ai/runtime](https://npmjs.com/package/@checksum-ai/runtime). A reviewer warns that "an incorrect change could also make a test pass while weakening the intended assertion", so healed PRs need review. **[THIRD-PARTY]** — [ToolRadar: Checksum](https://toolradar.com/tools/checksum-ai)
- **QA Wolf** structures cases as AAA (Arrange-Act-Assert) outlines before code is written, so the asserted outcome is fixed in a reviewable plan. **[VENDOR MKTG]** — [QA Wolf AI](https://www.qawolf.com/ai)

### Inferences
- The assertion-hallucination problem (for example `url_contains "#"`) is handled in two places. At authoring time, every assertion is executed against the live post-action state, so one that does not hold is never written. At heal time, assertions are frozen.
- A closed set of assertion types, each with a deterministic evaluator, is the standard. The open-ended "AI check" is a deliberately separate, costlier and explicitly fallible tier.

### Gaps
- No vendor documents a check for *vacuous* assertions, meaning ones that would also pass before the action, such as text present on the page before the click. None found does a before/after differential check at authoring time.

## 6. Waiting, synchronisation and flakiness handling

### Takeaway
Tools wait for stability before every action using several signals (network idle, DOM mutation quiescence, load events, screenshot stability). Compiled-code tools wrap runs with retries and traces. Meticulous removes nondeterminism at the source by stubbing the network and making the browser deterministic. Retries are paired with escalation, and flaky tests are quarantined rather than silently retried forever.

### Cited Findings
- **Momentic "smart waiting"** is on by default: "Momentic intelligently waits for the page to stabilize before performing each action". The default timeout is 3 s, configurable per test. Readiness signals are "Network idle" plus DOM readiness (load, DOMContentLoaded). It can be disabled in favour of explicit AI wait or Wait steps. **[OFFICIAL DOCS]** — [Momentic: Smart waiting](https://docs.momentic.ai/essentials/smart-waiting); [Momentic: Waiting for conditions](https://momentic.ai/docs/platform/waiting). Further inputs to smart waiting: "Navigation events, load events, Page screenshots, DOM changes (nodes added, removed, or updated), Same-origin requests". **[OFFICIAL DOCS]** — [Momentic: auto-heal](https://momentic.ai/docs/auto-heal)
- **Octomind**: the runtime adds "smart waits, auto-retries, and trace recording". **[VENDOR MKTG]** — [Octomind vs coding agents](https://octomind.dev/product/octomind-vs-coding-agents/)
- **Meticulous**: "because its browser runs deterministically, test suites with high flake rates should not flake on its platform". **[OFFICIAL DOCS]** — [Meticulous: Ingest existing tests](https://app.meticulous.ai/docs/session-recording/ingest-existing-tests). Third parties say it freezes time and randomness and uses a "deterministic scheduling engine". **[THIRD-PARTY]** — [qaskills: Meticulous visual testing guide](https://qaskills.sh/blog/meticulous-ai-visual-testing-guide); [G2 Meticulous](https://www.g2.com/products/meticulous/discuss)
- **QA Wolf**: "Any test that fails is automatically re-run. After multiple consecutive failures, a human steps in to investigate the root cause." It cites network hiccups and slow email servers as typical flake causes. **[OFFICIAL DOCS]** — [QA Wolf: Full Service FAQs](https://docs.qawolf.com/qawolf/Full-Service-FAQs). QA Wolf also acknowledges that flakes "can increase the overall runtime of your suite and slow your release velocity". **[VENDOR notes]** — [QA Wolf: Minimizing test flakes](https://qawolf.notion.site/Minimizing-test-flakes-69ad9a8115d447a0b518460b6f345dc8); [QA Wolf blog: Flaky coverage is fake coverage](https://qawolf.com/blog/flaky-coverage-is-fake-coverage)
- **Momentic** quarantine is the last tier of auto-maintenance: "removes an unresolved flaky test from the run" (see section 7). **[OFFICIAL DOCS]** — [Momentic: Auto-maintenance](https://momentic.ai/docs/reliability/auto-maintenance)
- **testRigor**: tests in a suite run in parallel, so "tests within a suite must be independent of each other". **[VENDOR TRAINING]** — [testRigor: Basics](https://testrigor.com/certification/basics-of-testrigor/)
- General practice: stub nondeterminism (clocks with Playwright's `page.clock.install()`, RNG, network). Retries "mask flakiness without addressing the root cause". **[THIRD-PARTY]** — [Tessl: flake pattern reference](https://tessl.io/registry/testland/flake-pattern-reference/files); [Claude skill: debug flaky tests](https://claudskills.com/skills/debug-flaky-tests/SKILL.md)

### Inferences
- Momentic's signal list (navigation, load, screenshots, DOM mutations, same-origin requests) amounts to a ready-made settle-detector spec. Note that it counts *same-origin* requests only, so third-party analytics beacons do not block network-idle.

### Gaps
- testRigor's waiting behaviour was not documented in the results.
- No vendor publishes measured flake rates.

## 7. Failure handling: auto-maintenance and heal flows, app bug vs test bug, human in the loop

### Takeaway
Mature tools use **tiered, least-invasive-first** repair. A per-run locator re-resolve that never edits the test comes first, then transient recovery steps, then a permanent heal gated by failure classification, then quarantine. **Real product regressions are explicitly not healed.** Permanent changes are always proposals that a human approves (Octomind, Momentic, Rainforest for manual steps, Checksum via PR). Playwright's Healer marks a test `fixme` or skipped when it believes the app itself is broken.

### Cited Findings
- **Momentic auto-maintenance tiers**: (1) locator auto-healing re-finds a stale element from the step description and applies only to the current run. (2) Transient recovery generates temporary steps to clear an obstruction such as a cookie banner, then retries. (3) Permanent healing, where "classification decides whether a failure is healable", repairs the test. (4) Quarantine. "Real product regressions and infrastructure failures are not repaired." **[OFFICIAL DOCS]** — [Momentic: Auto-maintenance](https://momentic.ai/docs/reliability/auto-maintenance)
- **Momentic failure recovery (beta)** applies only if the test passed at least once in the last 7 days, and runs at most once per test run. Successful changes await review in the results viewer, and runs can be slower. The docs list scenarios it declines, such as infrastructure issues. **[OFFICIAL DOCS]** — [Momentic: Failure recovery](https://momentic.ai/docs/platform/auto-healing/failure-recovery)
- **Momentic AI failure analysis** reviews recent steps and compares app state before and after key actions. Inputs are screenshots, URL and state, step descriptions, element-targeting details, and the error and stack. Output is an error summary, a root cause with potential fixes, raw error details, and a step summary. An MCP flow lets a coding agent read the saved classification and per-step artifacts "and decide whether a product bug or a test problem occurred". **[OFFICIAL DOCS]** — [Momentic: Failure analysis](https://momentic.ai/docs/failure-analysis); [Momentic: Coding agents comparison](https://momentic.ai/docs/comparisons/coding-agents)
- **Octomind** self-healing "analyzes the Playwright trace and DOM snapshot to separate real bugs from UI changes". It "never pushes code to your repository automatically", and "every fix starts as a pending proposal awaiting explicit approval". **[VENDOR MKTG]** — [Octomind: Playwright self-healing](https://octomind.dev/product/playwright-self-healing/). Auto-fix (beta) runs from the test result's auto-fix tab, and the user reviews the proposed solution. **[OFFICIAL DOCS]** — [Octomind: Auto-fix](https://octomind.dev/docs/maintain/auto-fix); [Octomind: Inspect broken tests](https://octomind.dev/docs/maintain-tests/inspect-broken-tests)
- **Playwright Healer**: the expected outcome is "a passing test, or a skipped test if the healer believes that functionality is broken". **[OFFICIAL DOCS]** — [playwright.dev: Test agents](https://playwright.dev/docs/test-agents). Third parties say that when the healer is confident the test is correct but cannot fix it, it marks the test `test.fixme()` and adds a comment before the failing step explaining the actual behaviour. **[THIRD-PARTY]** — [TestDino: Fixing Playwright tests with AI](https://testdino.com/blog/fixing-playwright-tests-with-ai); [Shiplight: Playwright agents](https://www.shiplight.ai/blog/playwright-agents)
- **Checksum**: with `auto-heal: true` (GitHub Action `checksum-ai/test-run-action@v1`) it "attempts real-time recovery during the test run. If the test still fails, it updates the Playwright test, opens a pull request with the proposed fix, and posts progress as a comment". **[PARTNER]** — [The CTO Club: Checksum CI/CD](https://thectoclub.com/partner-spotlight/checksum/how-to-use-checksum-for-continuous-e2e-testing-in-ci-cd/). About 70% of breaks auto-resolve, per a vendor-stated figure. **[THIRD-PARTY relaying vendor]** — [ToolRadar: Checksum](https://toolradar.com/tools/checksum-ai)
- **Rainforest** self-healing AI blocks work like this: "If any step in that block fails during a run, Rainforest automatically tries to regenerate the steps and self-heal. If it succeeds, your test is updated automatically." **[OFFICIAL DOCS]** — [Rainforest: Self-healing tests with AI blocks](https://help.rainforestqa.com/docs/how-to-generate-self-healing-tests). For manually built steps, the AI suggests a fix for a person to approve. **[VENDOR BLOG]** — [Rainforest: AI test automation](https://www.rainforestqa.com/blog/ai-test-automation)
- **Reflect's agent** can "delete and retry steps when something fails" during authoring. **[VENDOR BLOG]** — [SmartBear: Agentic test creation](https://smartbear.com/blog/agentic-test-creation-with-reflect)
- **Autify Nexus** "Fix with AI" flags the failed result and asks whether you would like the AI to find an alternative locator. **[VENDOR MKTG]** — [Autify Nexus](https://autify.com/products/autify-nexus)
- **Functionize** claims its Execute Agent "auto-detects and fixes broken steps with 200+ AI signals live during test runs". This comes from a competitor comparison page. **[VENDOR MKTG]** — [Functionize vs Mabl](https://www.functionize.com/page/functionize-vs-mabl)
- **QA Wolf**: problems with the test itself are kept separate from real bugs. Flows needing large fixes are disabled and placed in maintenance mode, and human-verified bugs are passed to developers. **[OFFICIAL DOCS]** — [QA Wolf: Full Service FAQs](https://docs.qawolf.com/qawolf/Full-Service-FAQs)
- **Virtuoso** claims about 95% self-heal accuracy. **[VENDOR MKTG]** — [Virtuoso: AI-powered test automation](https://virtuosoqa.com/solutions/ai-powered-test-automation)

### Inferences
- "A model proposes, it never writes" (this repo's D-27) is industry consensus for **permanent** changes. Only Rainforest's AI blocks auto-commit heals, and only for steps that were AI-generated in the first place.
- The separation that matters is **per-run healing (ephemeral) vs permanent test edits (reviewed)**. Momentic's per-run locator re-resolve lets a run continue without touching the saved test.
- The guard against masking real bugs is classification before healing, plus an eligibility rule such as "passed in the last 7 days", which means a fresh failure on a stable test.

### Gaps
- No vendor publishes precision or recall for bug-vs-test-issue classification.

## 8. Test data: generated emails and phones, temporary inboxes, SMS and 2FA

### Takeaway
Tools give each run a fresh, real inbox or phone number (Momentic ephemeral inboxes, testRigor via Twilio). They extract OTPs with a regex and a time filter so a stale code is never picked up, and they compute TOTP from a stored secret. Credentials are supplied by humans and reused through a login dependency.

### Cited Findings
- **Momentic**: inboxes on `@usemomentic.com` or `@gomomentic.com`. Use a permanent one, or provision an **ephemeral inbox at runtime**, which is auto-deleted after 24 h and suits sign-up flows. A JavaScript step calls `email.fetchLatest`, applies the regex `/\b\d{6}\b/`, and saves the result with `setVariable` for use as `{{ env.OTP_CODE }}`. "Always pass afterDate to avoid matching a stale code from a previous run", and set a timeout. **[OFFICIAL DOCS]** — [Momentic: Sending and receiving emails](https://momentic.ai/docs/platform/email); [Momentic: Email OTP guide](https://momentic.ai/docs/guides/auth/email-otp). A dedicated inbox name must be reserved through support. **[OFFICIAL SUPPORT]** — [Momentic support: email OTP](https://support.momentic.ai/articles/3721608818-how-do-i-log-in-using-email-otp-codes)
- **testRigor**: plain-English steps check that an SMS or email arrived, match a code template such as "######", and save it. SMS needs the Twilio integration. A step allocates a **temporary phone number** into a variable, "Twilio charges will apply", and the number is released after the run. TOTP codes are generated from a stored QR code image. **[VENDOR BLOG / TRAINING]** — [testRigor: SMS/2FA and phone call testing](https://testrigor.com/how-to-articles/how-to-do-sms-2fa-and-phone-call-testing-using-testrigor/); [testRigor: TOTP 2FA](https://testrigor.com/how-to-articles/how-to-automate-2fa-login-with-totp-using-testrigor/); [testRigor: SMS and phone calls](https://testrigor.com/certification/sms-and-phone-calls/); [testRigor: unique test data](https://testrigor.com/how-to-articles/how-to-generate-unique-test-data-in-testrigor/)
- **Octomind** asks for test credentials for username/password logins and supports 2FA and captcha. **[OFFICIAL DOCS]** — [Octomind: recommended tests](https://octomind.dev/docs/build-tests/recommended-tests)
- **QA Wolf** names slow email servers as a typical flake source. **[OFFICIAL DOCS]** — [QA Wolf: Full Service FAQs](https://docs.qawolf.com/qawolf/Full-Service-FAQs)

### Inferences
- The `afterDate` filter (only accept messages newer than this run's start) is the small, structural detail that makes inbox-based OTP non-flaky.

### Gaps
- No detail was found on testRigor's own generator for unique emails or names beyond the how-to title, and nothing on whether it provisions inboxes itself.

## Adoptable techniques for our pipeline

### Takeaway
Our pipeline already matches the market on its strongest structural point: deterministic grounding against discovered elements, which is the same idea as Playwright MCP refs and Momentic's cached fingerprints. The biggest gaps against the market are four. We generate steps for later screens without observing each screen first. Our discovery action space is links only. Control *type* comes from LLM wording, not the a11y role. Assertions are not executed at authoring time. Each technique below is mapped to weak points (1)–(5), with its source.

### Cited Findings (technique, then where it comes from)

**(1) Discovery only follows `<a href>`, so button-driven SPAs are under-discovered**
- **1a. Event-based crawl (Crawljax pattern).** On each discovered screen, enumerate candidate clickables from the a11y tree and DOM (`role=button|link|tab|menuitem`, `[onclick]`, `[tabindex]`, `<summary>`), click each, then compare the post-click DOM against known screens with a *structural* equivalence function (ignore text). Record a new screen plus a transition edge, and reset by reloading the screen's URL and replaying the click path. This is a direct structural fix that matches our screen-fingerprint work. — [Crawljax ICSE 2009](https://people.ece.ubc.ca/amesbah/resources/papers/icse09.pdf); [RIA crawling survey](https://www.site.uottawa.ca/~bochmann/Curriculum/Pub/2012%20-%20Crawling%20Rich%20Internet%20Applications%20-%20The%20state%20of%20the%20art.pdf)
- **1b. Bound state explosion with breadth-first search, a per-state action budget, a global timeout, and stop-on-no-new-states.** — [AutoE2E arXiv 2408.01894](https://arxiv.org/abs/2408.01894v2)
- **1c. Make exploration side-effect-free.** While discovery is clicking buttons, intercept every non-GET request with `page.route` and fulfil it with a stub or abort it, the way Meticulous stubs all HTTP so replays touch no backend. Also skip actions whose accessible name matches a destructive lexicon (delete, remove, pay, place order, sign out), mirroring AutoE2E's "non-critical actions only" (third-party description) and the tiered-permission guardrail pattern. Per CLAUDE.md, the lexicon is a secondary filter and the request-method block is the structural one. — [Meticulous network stubbing](https://app.meticulous.ai/docs/concepts/network-recording-and-patching); [AutoE2E write-up](https://zenn.dev/mima_ita/articles/ce1185307264a5?locale=en); [Apidog guardrails](https://apidog.com/blog/ai-agent-guardrails/)
- **1d. Detect the cookie banner and login wall first.** Make login an explicit *dependency* that discovery replays before exploring, as Octomind and QA Wolf Mapping do. We already keep credentials as `${env:}` references, so the dependency stores references, not literals. — [Octomind recommended tests](https://octomind.dev/docs/build-tests/recommended-tests); [QA Wolf: Map workflows](https://docs.qawolf.com/qawolf/Map-your-app-s-workflows-2a45b2a994fb80ca8a87c8fdc2a443fc)
- **1e. Accept documentation as discovery input** (PRDs, help docs, Jira) so the planner knows features that crawling cannot reach. — [QA Wolf Mapping AI](https://www.qawolf.com/mapping-ai); [Autify Nexus](https://info.autify.com/nexus-ppc)

**(2) The LLM sees only the entry page when writing steps, so it invents or drops later steps**
- **2a. Switch from "write all steps, then replay" to an act-observe-write loop.** For step *i*, replay steps 1..i-1, capture the *current* screen, give the LLM only that screen's control list, accept one step, ground it, execute it, and repeat. This is how the Playwright Generator ("performs the scenarios live"), QA Wolf's Automation Agent ("performing the test manually"), Reflect's MCP agent and Rainforest's VM author tests. Our live replay already captures later screens, so the change is moving the LLM call *inside* the replay loop. — [playwright.dev test agents](https://playwright.dev/docs/test-agents); [Medium guide quoting docs](https://medium.com/@ismailsobhy/ai-powered-test-automation-part-4-complete-guide-to-playwright-agents-planner-generator-healer-d418166afe34); [QA Wolf platform](https://www.qawolf.com/platform); [SmartBear agentic Reflect](https://smartbear.com/blog/agentic-test-creation-with-reflect); [Rainforest AI test creation](https://help.rainforestqa.com/docs/ai-powered-test-creation)
- **2b. Keep a two-level representation.** First a human-readable plan (Planner Markdown, QA Wolf AAA outline, testRigor case names) with intended outcomes, then per-screen step grounding. The plan is the cheap human-review point, and steps for screen *k* are generated against screen *k*'s snapshot. — [playwright.dev test agents](https://playwright.dev/docs/test-agents); [QA Wolf AI](https://www.qawolf.com/ai); [testRigor AI test case generation](https://testrigor.com/certification/ai-driven-test-case-generation-with-testrigor/)
- **2c. Ref-only targeting.** Give the LLM the current screen as an a11y snapshot with opaque IDs (`e1…eN`) and require every step to reference an ID that exists in that snapshot. Invalidate IDs on every page change. An invented element then cannot be expressed in the schema at all: a Zod enum of the screen's IDs, a structural check rather than a regex over prose. — [Playwright MCP snapshots](https://playwright.dev/mcp/snapshots)
- **2d. Let the authoring agent delete and retry a step that fails during authoring** rather than failing the whole case, as Reflect's agent does. — [SmartBear agentic Reflect](https://smartbear.com/blog/agentic-test-creation-with-reflect)

**(3) Multi-step forms on one URL**
- **3a. Treat screens as DOM states, not URLs.** Take a fresh snapshot after *every* action ("refs are valid until the page changes"). A wizard's step 2 is a new screen even if the URL is the same, which is Crawljax's DOM-state model. — [Playwright MCP snapshots](https://playwright.dev/mcp/snapshots); [Crawljax TSE 2011](https://people.ece.ubc.ca/amesbah/resources/papers/tse11.pdf)
- **3b. Multi-signal settle detection before capturing the next screen.** Use navigation and load events, DOM-mutation quiescence, same-origin network idle, and screenshot stability, with a short default timeout (Momentic uses 3 s). Counting only same-origin requests avoids analytics beacons blocking idle. — [Momentic smart waiting](https://docs.momentic.ai/essentials/smart-waiting); [Momentic auto-heal (inputs)](https://momentic.ai/docs/auto-heal)
- **3c. Transient recovery during replay.** If an overlay (cookie banner, modal) blocks the next grounded step, insert temporary dismiss steps for that run only and retry, without changing the saved test. — [Momentic auto-maintenance](https://momentic.ai/docs/reliability/auto-maintenance)

**(4) The LLM's wording ("combobox", "select") does not match the real control**
- **4a. Never trust the model's control-type word.** Take role and accessible name from the captured a11y tree for the chosen element (Playwright MCP's verify tools take "the element's ROLE from the snapshot"). Derive the *action* deterministically from the actual role: a native `<select>` gets `selectOption`, an ARIA combobox gets click then option, a textbox gets fill. Our IR would then store the discovered role, not the LLM's noun. — [Playwright MCP test assertions](https://www.mintlify.com/microsoft/playwright-mcp/tools/test-assertions)
- **4b. Generate locators from the chosen element** (Playwright MCP `browser_generate_locator`, Virtuoso deriving XPath/CSS on first run). Store **several** selectors per element (Virtuoso keeps XPath, XPath ID and CSS) and use the first that resolves at run time. — [Playwright MCP tools](https://www.mintlify.com/microsoft/playwright-mcp/tools/test-assertions); [Virtuoso KB: selectors](https://knowledge.virtuoso.qa/hc/en-us/articles/19510251689501-Virtuoso-is-targeting-unexpected-element-type-that-has-the-same-hints); [Virtuoso KB: selector preference](https://knowledge.virtuoso.qa/hc/en-us/articles/19642758521373-Preference-in-choosing-the-selectors-during-element-identification-while-test-authoring)
- **4c. Disambiguate duplicates by relative position to a visible anchor** ("the 'Edit' button to the right of 'Invoice 42'", "top 'Login'"), not by nth-index alone. This is testRigor's target/anchor model and Virtuoso's position hints. — [testRigor: UI-position references](https://testrigor.com/blog/how-to-reference-elements-by-ui-position-using-testrigor); [Virtuoso KB](https://knowledge.virtuoso.qa/hc/en-us/articles/19510251689501-Virtuoso-is-targeting-unexpected-element-type-that-has-the-same-hints)
- **4d. Multi-signal element fingerprint with a semantic fallback.** Persist css, attributes, role, accessible name, bounding box and screenshot crop per grounded step. At replay, a fingerprint mismatch triggers a semantic re-resolve from the step's *description* for that run only, and a permanent change goes through review. The cache key is step ID plus parent module plus resolved description plus template values. — [Momentic step cache](https://momentic.ai/docs/reliability/step-cache); [Momentic self-healing blog](https://momentic.ai/blog/self-healing-test-automation-guide)

**(5) Hallucinated assertions (e.g. `url_contains "#"`)**
- **5a. Execute every assertion at authoring time against the live post-action state.** Reject any assertion that does not hold, and feed the actual value back (the real URL, the real visible text) in the rejection message, as the Playwright Generator "verifies selectors and assertions" live. — [Medium guide quoting playwright.dev](https://medium.com/@ismailsobhy/ai-powered-test-automation-part-4-complete-guide-to-playwright-agents-planner-generator-healer-d418166afe34)
- **5b. Use a closed assertion catalog, each with a deterministic evaluator**: element visible by role and name, text visible, list visible, field value (Playwright MCP verify tools). Keep any natural-language or AI check as a separate, explicitly fallible tier that is never cached, as Momentic and testRigor do. Prefer deterministic text checks, which Momentic calls "deterministic and cheaper". — [Playwright MCP test assertions](https://www.mintlify.com/microsoft/playwright-mcp/tools/test-assertions); [Momentic mobile assert](https://momentic.ai/docs/reference/mobile-commands/assert.md); [testRigor validations](https://testrigor.com/certification/validations/)
- **5c. Before/after differential check, our own extension.** Reject an assertion that *also* holds on the pre-action state, because it is vacuous. No vendor documents this, but it follows from 5a and closes the "some action happened, not the right one" class (TD-01). — inference built on [Playwright test agents](https://playwright.dev/docs/test-agents)
- **5d. Freeze assertions during healing.** A heal may change actions but not assertions, as in Checksum's runtime model. Any heal that touches an assertion becomes a human-review item. — [npm @checksum-ai/runtime](https://npmjs.com/package/@checksum-ai/runtime); [ToolRadar Checksum review note](https://toolradar.com/tools/checksum-ai)
- **5e. Pin the expected outcome in the plan (AAA outline) before steps exist.** Generated assertions must then be traceable to a plan outcome, not invented from page text. — [QA Wolf AI](https://www.qawolf.com/ai)

**Cross-cutting (failure handling and data)**
- **Tiered repair**: per-run re-resolve, then transient recovery, then classified permanent heal (only for tests that passed recently), then quarantine. Never heal a suspected app regression. Mark it `fixme` or skipped with an explanatory comment, as the Playwright Healer does. — [Momentic auto-maintenance](https://momentic.ai/docs/reliability/auto-maintenance); [Momentic failure recovery](https://momentic.ai/docs/platform/auto-healing/failure-recovery); [playwright.dev test agents](https://playwright.dev/docs/test-agents)
- **Retry, then escalate after N consecutive failures** rather than retrying indefinitely. — [QA Wolf FAQs](https://docs.qawolf.com/qawolf/Full-Service-FAQs)
- **Ephemeral per-run inbox plus `afterDate` filter** for OTP and sign-up flows, and TOTP from a stored secret held only in an env reference. — [Momentic email OTP](https://momentic.ai/docs/guides/auth/email-otp); [testRigor TOTP](https://testrigor.com/how-to-articles/how-to-automate-2fa-login-with-totp-using-testrigor/)
- **Failure-analysis input bundle** for our Gemini vision diagnosis step: recent step screenshots before and after, URL and state, step descriptions, element-targeting details, and the error and stack. — [Momentic failure analysis](https://momentic.ai/docs/failure-analysis)

### Inferences
- Priority by expected impact on our weak points: **2a + 2c** (act-observe-write with ref-only targeting) addresses (2) and much of (3) and (4) at once. **5a + 5b** fixes (5) structurally. **1a + 1c** fixes (1) safely. **4a** is a small, contained change to how grounding records control type.
- 2c and 4a fit this repo's central rule: they replace prompt-level instructions ("use only real elements", "call it a combobox") with schema-level and structural checks (an enum of screen element IDs, role read from the a11y tree).
- 1c's request-method blocking is the structural guard. A destructive-word lexicon is a text heuristic and should only ever be the secondary filter.

### Gaps
- None of these techniques' effectiveness is independently benchmarked. Vendor success figures (Momentic 99% cache hits, Checksum 70% auto-resolve, Virtuoso 95% heal accuracy, Functionize 99.95% tracking) are all self-reported.
- Whether AutoE2E actually separates critical from non-critical actions, and how, needs reading the paper (search budget exhausted).
- 5c (the vacuous-assertion differential) has no vendor precedent found. It is our own proposal and should be validated by artifact replay on saved `runs/` before adoption.
