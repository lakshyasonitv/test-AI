## 2. The Project Brain gap

### 2.1 What the rule says

`CLAUDE.md:201-214` and `AGENTS.md:201-214` (identical): read `project-brain/03-progress.md` and the
newest file in `project-brain/journal/` at the START of every session, give a 2-line "where we left
off", update the brain at the end of **every** session that changes anything, and suggest `/brain log`.

### 2.2 What is actually there

| Check | Command | Result |
|---|---|---|
| Directory present? | `ls project-brain/` | **No such file or directory** |
| Ever committed? | `git log --all -- '*project-brain*'` | **zero commits** |
| Deliberately ignored? | `grep -i brain .gitignore` | **no match** |
| Tracked under another path? | `git ls-files \| grep -i brain` | **nothing** |
| Referenced anywhere but the two guidance files? | `grep -rn "project-brain\|/brain\b" --include=*.{md,ts,js,json,yml}` | **only `CLAUDE.md` and `AGENTS.md`** |

So it is not deleted and not deliberately local — it was **never added to git**. It exists only as
untracked files on the machine of whoever wrote the rule.

### 2.3 The second half of the gap

`.gitignore:8` ignores **`.claude/`**, and `ls -a .claude/` on this clone returns *No such file or
directory*. A project slash command lives in `.claude/commands/`. So the rule instructs an agent to
suggest `/brain log` — a command that **cannot reach any teammate** by design of the ignore file.

### 2.4 Provenance

Both commits are by the same author, `Lakshya Soni <lakshya.soni@thinkvibes.com>`:

- `c6c4524` first introduced the Project Brain block.
- `3a9c41c` (2026-09-19) strengthened it to "every session". Its message is unusually informative and
  is the best evidence of intent — it documents the failure that motivated the rule: *"A single
  unlogged commit left the brain wrong in five ways at once: the fix itself absent, the test baseline
  35 tests light (1421 recorded against 1456 actual), two shipped items still listed as open work,
  the deploy list short by one, and stale dates."*

The same message states the rule is kept in both files deliberately — *"they are deliberate mirrors
… updating one would create exactly the drift DECISIONS.md D-01 exists to prevent"* — and
`diff CLAUDE.md AGENTS.md` confirms it: **exactly three differing lines** (line 1 title, line 3 agent
name, line 25 self-reference row). Any edit to this rule must be made in both files.

### 2.5 A self-violation the same commit admits

`CLAUDE.md:4` says *"Keep this file itself under 200 lines"*. `wc -l` gives **214** for both files.
`3a9c41c`'s message acknowledges it: *"Note both files now run 214 lines, past the 200-line cap they
state about themselves — already tracked as a task."* Tracked **in the brain**, which is unreadable
here. That circularity is the gap in miniature.

### 2.6 Assessment

The rule sits in two committed files, both addressed to *any* agent in the repo, and both instruct
reading a path that has never existed in the repo. The intent was clearly a **shared** brain; the
directory simply never got added. Consequence: every session on every clone but one fails at step
one of its own onboarding instructions.

Three options were put to the requester, who chose **A**:

- **A — commit `project-brain/`.** Matches intent. Two caveats: it restates what `TECH_DEBT.md` and
  `DECISIONS.md` own, so it needs the same subordination header `docs/LLM_CONTEXT_BRIEFING.md`
  carries; and it may hold notes nobody meant to publish.
- **B — declare it local-only.** Add to `.gitignore`, reword to "read if present". Cheap, but leaves
  a committed shared file describing a private artifact.
- **C — bootstrap a brain here.** **Rejected.** Progress and a test baseline are reconstructible from
  git log and `TECH_DEBT.md`, but the journal and the cited 2026-09-18 decision record are not.
  Fabricating them produces exactly the untrustworthy brain the rule exists to prevent.

Changes needed: commit the directory (needs the author — cannot be created from nothing here);
un-ignore `.claude/commands/` so `/brain log` ships; make the rule degrade gracefully when the brain
is absent, **in both files**; and fix the 214→200 line overflow.

## 3. Item 7 — locale, timezone, Accept-Language

### 3.1 Evidence

`grep -rni "locale\|timezoneId\|Accept-Language\|extraHTTPHeaders" --include=*.ts src/` →
**no browser configuration anywhere**. All 8 matches are unrelated: `toLocaleString` in
`gemini.ts:66-67` and `htmlReport.ts:222`, `localeCompare` in `runStore.ts:207`,
`library.ts:185,430`, `projects.ts:115`, and a comment about URL locale prefixes in
`hybridDiscovery.ts:1127`.

Five browsers are opened, none pinned:

| # | Site | Code | Context options possible? |
|---|---|---|---|
| 1 | `domDiscovery.ts:538-539` | `chromium.launch(chromiumLaunchOptions())` → `browser.newPage()` | yes — `newPage(opts)` |
| 2 | `hybridDiscovery.ts:280-282` | same → `browser.newPage()` | yes |
| 3 | `hybridDiscovery.ts:895-896` | same → `browser.newContext()` (no args) | yes, already a context |
| 4 | `liveExtend.ts:169-171` | same → `browser.newPage()` | yes |
| 5 | `playwright.config.ts` `use:` | the generated spec's runner | yes — `use.locale` |

`src/browserLaunch.ts` is the existing single seam and its own docblock enumerates **the same five
consumers**, with the rationale: *"a misconfiguration that passes `--no-sandbox` to only some of the
five consumers is worse than missing it entirely."* That argument transfers to locale verbatim, which
is why the plan adds a sibling helper there rather than inlining.

`playwright.config.ts`'s `use:` block sets `headless`, `trace`, `screenshot`, `video`,
`launchOptions` — and **no** `locale`, `timezoneId` or `extraHTTPHeaders`.

### 3.2 Causal chain for the Korean output

Locale is a **context** option; `chromium.launch()` does not accept it, which is why a launch-options
helper alone was never going to cover this. Unpinned `Accept-Language` at sites 1–3 → site serves
Korean → cheerio extracts Korean accessible names into `AppModel.pages[].elements` → Gemini receives a
Korean AppModel and writes Korean cases. **The model is behaving correctly**; it describes the page it
was shown. Korean then propagates to case titles, IR targets and generated locators.

Conclusion carried into the plan: the poison enters at **discovery**, so the fix must be at the
browser. A prompt saying "write in English" is a preference over a constraint — the anti-pattern
`CLAUDE.md` names — and would leave the AppModel, locators and executed spec Korean.

### 3.3 Two traps found while checking the fix

- **`newContext()` is the wrong instrument.** Rewriting sites 1/2/4 as `newContext()` +
  `context.newPage()` walks into TD-41 / D-23: `sessionStorage` is tab-scoped, so a second page comes
  back logged out. `CLAUDE.md` calls this out and says keep the flow on the SAME page.
  `browser.newPage(options)` accepts the full context option set, so the diff is one line per site
  with no restructuring. **This claim is an API-surface assertion and is exactly what D-19 says must
  be executed once, not just `tsc`-checked** — see §8.
- **The cache key is a hard dependency, not a follow-up.** `RUN_LOCALE` is a new real input
  dimension. TD-22 / D-10 say a key missing a dimension serves a wrong answer forever, and TD-94
  records this having already shipped once (an empty LLM result cached permanently). Miss it and every
  cached Korean answer is served forever, so the fix appears not to work.

### 3.4 The per-run setting is a clean additive fit

`src/server/index.ts:221` destructures `{ prompt, url, urls, coverage, options, projectId }` — an
`options` object **already exists**. Lines 242-246 forward it through an explicit allow-list with the
comment *"Only the two known booleans are forwarded — the body is untrusted input, and spreading it
straight into runPipeline would let a caller set anything."* A third validated key fits this pattern
exactly and satisfies platform rule 1 (optional additive fields only).

Client side: `public/app.js:3186` sends the body and `:3174` asserts in a comment that it is
*"byte-for-byte the shape it always was: { prompt, url, coverage, options }"* — that comment must be
updated in the same commit. `app.js:5119-5121` is "Run options — the Settings popover", explicitly
*"per-run request options, not persisted server settings"* — the right home for the control.

## 5. Item 5 — step cap and return-to-start

The machinery exists; this is mostly reuse. `schema/ir.ts:84-86` defines `meta.truncated` and
`hasTerminalAssertion`, with the note that a truncated IR without a terminal assertion **cannot report
"passed"** — a guarantee the cap inherits for free. `ir.ts:1967-1974` already builds a truncated IR
from a step prefix and records a `truncationNote`.

No cap exists: `schema/ir.ts:105` is `steps: z.array(Step).min(1)` — **no upper bound** — and
`grep MAX_STEPS` finds nothing. But `.env.example:82-134` establishes a documented `MAX_*` convention
(`MAX_LLM_CALLS_PER_RUN`, `MAX_IR_ATTEMPTS`, `MAX_LIVE_EXTENSIONS`, `MAX_CONCURRENT_RUNS`,
`MAX_LOGIN_CASES`, `MAX_CASE_REGEN_ATTEMPTS`, `MAX_ACCUMULATED_CASES`), so `MAX_STEPS_PER_CASE` has an
obvious shape and an obvious home.

Return-to-start is the risky half. `pageKey()` is shared between `testCases.ts:171` and `ir.ts` so the
two *"cannot disagree about which cases are login cases"* — the same shared comparison is the right
structural basis for "same page". `ir.ts:99-110` already special-cases `url_contains` and
`PAGE_LEVEL_ASSERTIONS` during grounding, the precedent for reading page identity there.

**Unresolved, and flagged as blocking Q3:** whether the intended rule is "return to start between
independent checks" or "one page per case unless inherently multi-page". They produce different
guards, and a wrong one breaks legitimate compound flows (login → dashboard → settings). TD-37 is that
exact mistake on record — an assertion generalised from login to any form with a preceding fill.

## 6. Item 8 — case selection

**Root cause located exactly, and it is not a bug.** `selectCases` at `testCases.ts:160` was read in
full. Its own comment at `:198-201` states the design: *"Diversity before depth. Filling the budget by
raw priority produces five flavours of the same check; a capped suite is only defensible if the few
cases in it cover different ground."*

Mechanism:

- `:203` — `const primary = kept.find(c => c.fromPrompt)`. **Singular.** Exactly one prompt-derived
  case is protected.
- `:207-212` — the diversity pass takes one case per distinct `category`, skipping any category
  already seen.
- `:213-216` — leftover slots filled by priority.

So every slot after the first is awarded for **category novelty**. A "voice search" case in an unseen
category outranks a second highly-relevant case in a seen category. The reported symptom is the code
working as designed, which is why the fix must re-argue the original decision in `DECISIONS.md` rather
than quietly drop it.

Two guardrails found in the surrounding code:

- `finalizeCaseSelection` `:232` and its docblock `:218-231`: when the human gate was used the list is
  *"already the human's final, explicit decision"* and re-applying budget logic *"silently overrides it
  in either direction."* Item 8 must touch the **ungated** path only — otherwise it overrides a human
  decision, violating platform rule 6 (*a model proposes, it never writes*).
- `fromPrompt` is a **model self-report**, so by the central design rule it is a preference until a
  deterministic check backs it. `filterByScope` is described at `:227` as *"a defensive floor, not a
  count constraint"* — the right place for that check. The check must be structural (`pageKey()`
  against resolved entry URLs), **not** keyword-matching the prompt against titles: that is TD-01
  restated. `titleOverlap` already does prose comparison for dedup and that is as far as it should go.
